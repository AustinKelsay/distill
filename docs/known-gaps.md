# Known gaps

What DISTILL does not do, or does only partly. Update this page when a change adds or removes a limit.

## Capture

- With any privacy exclusion set, a harness whose sessions record no working directory is not archived at all: Antigravity, Hermes's session files, and Cursor (its stores and transcripts). Neither is a T3 Code thread whose worktree and project root are unknown, nor new native references for it.
- Cursor's IDE chat store (`state.vscdb`) is not read: in the chats checked for #108, each chat with messages also had an agent transcript, which DISTILL archives, but the transcripts keep no tool results or reasoning; only the store has them (`docs/cursor-ide-chats.md`). A chat kept only in the store is missed. Cursor's SDK agent stores (`projects/*/sdk-agent-store`, how T3 Code runs Cursor) encrypt their blobs, so they are archived but not parsed; their agents are covered by Cursor's transcripts and the T3 threads that ran them.
- OpenCode's spilled tool outputs are looked for only in `tool-output/` beside the database DISTILL reads. With `OPENCODE_DB` set elsewhere they are not captured.
- Format drift inside a record type a parser knows (a renamed field) is not counted; only a capture that then parses to nothing shows it.
- A config that lists every harness DISTILL knew when it was written gets new harnesses switched on; one that lists only some gets nothing added.
- Each new capture costs two directory fsyncs (about 18 ms), so a first sweep of a large machine takes a few minutes.

## Findings

- Names, postal addresses, phone numbers and companies are found only by the model pass, only in what the owner and the agent wrote, and only once it has run. A detail cut across two parts of a long session can be missed. Personal details are not masked for a trusted reader.
- Findings go out of date when the fingerprint key changes: a lost key means every session is scanned again, and old fingerprints match nothing new.
- A model reply that is not the expected JSON fails under the strict parse; that session is retried after the rest.

## Search

- Words longer than 64 characters are not indexed, and there is no phrase or prefix search.
- Words inside encoded data are not indexed: a run of at least 100 bytes of base64's characters (letters, digits, `+`, `/`, `=`, `_`, `-`) with a digit in it (#154). On the owner's archive that was half of the tool output and 97% of the distinct words. A token that long without a `.`, a space or another separator, such as a long hex string, is not found either.
- Tags are shown, filtered and word-indexed in their standard form, through the owner's aliases and the owner's own tags (#158, added or hidden in the window or with `distill tag`, never through MCP); an edit or a new alias reaches word search at the next tick. A tag with a personal detail in it is shown as written, so its cover still fits. The owner's tags show only on a session with a current card. The list of tags in use (`distill tags`, `list_tags`, the Sessions chips) counts the sessions' current cards and leaves out a tag with a finding in it. A filter by several tags means all of them (#159); there is no any-of and no prefix match. The window's tag field holds several tags with spaces between them, so a tag typed there with a space in it is taken as two (a tag's standard form has `-` for spaces).
- Search by meaning embeds only what the owner wrote and the card summary. Mirrors and sessions that worked inside the home (the steward mark) get no vectors, so `--mirrors` and `--steward` find them by words only. No prefix such as `search_query:` is added for embedding models that expect one. A search by meaning reads the whole vectors file and embeds the query once in Ollama, unless the detector finds a secret in it or a piece of it (split at spaces, `=`, `:`, `,`, `;`, quotes and round brackets) 8 or more bytes long has a short fingerprint already in the word index. A secret both checks miss is embedded as written: a shorter piece, one joined to other text by any other character (`.`, `?`, `/`, `-`, square brackets…), or one not yet indexed. So are personal details.
- A card written by a tick can be embedded in the same tick (within the vectors step's own limit) but joins the word index at the next one, because the index step runs before the card step.
- Measured on the owner's archive (#117): asked the way the owner would say it, 16 of 24 sessions the owner started were in the top five. That set is the yardstick for any search change.

## Safety checks

- The exposure check sees listeners only through `lsof`, and only DISTILL's own processes running at the time; without `lsof` that rule is unchecked. On Linux the disk counts as encrypted only on a dm-crypt device. The timer's unit files sit outside the home with the usual modes; they hold paths, not session data.
- The pruning check reads the owner's own harness settings and Claude Code's managed settings, not project-level settings, MDM profiles or server-managed settings. Antigravity's trimming by size and in-place rewrites have no setting to read (`docs/harness-pruning.md`).
- Whether a model is stored on this machine is read from `OLLAMA_MODELS`, else `~/.ollama/models`; an Ollama server started with another model folder cannot be checked. With `[steward.generation]` set, a card or detail model counts as there when the provider's `/models` lists it.
- The read log notices edits; it doesn't prevent them (ADR 0005). Each line carries the SHA-256 of the chained line before it, so a chained line changed or taken out before another shows as a warning in status, the Overview and the Read log screen, and fails `distill verify` (#161). Lines an older build wrote, or an older build still running appends without the lock (an MCP server started before an install), carry none and are not in the chain: one of them changed, taken out or put in is not seen. The newest lines can be taken off the end, and `prev` stripped from a line to the end, without a break: a backup run notices that only when the log no longer starts with what it stored before, or is gone, so only on a home with backups, and only for what had been backed up. Once seen, a warning stays: each later run to that target says it again from its encrypted record. A home restored from the run that first saw a rewrite says so only after its next run to that target. A backup made by a build before the read log was stored in parts (record version 1) is not compared.
- What left this machine (#162; status, the Overview) is counted from the read log and the backup log, for the last day and the last 7 days: reads that served something, by the model and provider that read, and backup runs with the bytes they stored, encrypted (a run that failed partway counts its bytes, not as a run; a scheduled run stopped at its deadline writes no backup log line, so the bytes it stored, which later runs reuse, are not counted). A list or search counts its rows (`listed`) but not which sessions they were, so sessions listed twice are counted twice. A read by a model in Ollama counts where its read log line says Ollama served it from (`via`); a line written before builds logged that is judged by what Ollama has on this machine when status runs, so until 7 days after the last such line (an older MCP server still running writes them too), a removed model's older reads count as `ollama-cloud` and a cloud model since pulled here counts as staying. The counts are only as whole as the logs: when the read log has been edited they say they may be short.

## Backups

- Backups so far: `distill backup init` makes the backup key and prints it once; `distill backup run` copies to each `[[backup]]` target. The `folder` kind is built in; any other kind is an adapter, `distill-backup-<kind>` on `PATH` (`docs/backup-adapters.md`). Two ship: `ssh` and `rclone` (which covers S3-compatible stores); there is no restic bridge, since restic keeps snapshots rather than single objects. The rclone adapter checks for an object and then uploads it, so two puts of one name at once can both upload on a store with no conditional write, the later one winning. Both read their settings as plain text and refuse one with a quote or backslash in it. An adapter target is added by hand in config.toml (Setup adds only folders), and its settings sit there as written, so a credential in one is as private as the config. DISTILL starts the adapter for each use of a target (each run, test, verify, restore, and each tick, to see whether it was started) and waits on it with no time limit, so an adapter that hangs holds up that run or tick. Each object goes to it through a file in the system's temporary folder, owner-only and removed after; what it prints on standard error goes to the terminal or the tick's log. `distill backup verify` checks that a target holds its newest run, by name or, with `--full`, by fetching and decrypting every object. The window's Setup has a Backups step that adds folder targets (by hand in config.toml otherwise; the CLI has no `backup add`), tests each, and makes the backup key or shows it again; Finish starts the first backup to each folder that has none, and refuses a new folder under the name of one that has backups (a target's runs go by its name; after a new backup key, that includes the original folder added back under its old name); the Overview has a Backups section with Back up now and Verify (by name only; `--full` is CLI only). A test of a folder target writes one small file there and removes it; a test of an adapter target is what the adapter checks when told `probe`, and DISTILL sends it no object. `distill backup status` and the status report say where each target stands.
- The tick backs up only to targets the owner has started (`distill backup run`, Back up now, or Setup's Finish, which starts one to each folder), so it never makes a target's folder, and starts a target over only after the owner makes a new backup key. A first run that stops early (the window closed during it) is finished by the next tick, which goes on from the objects already sent; one that stopped before making the target's `distill-backup/` waits for the owner. The tick can't tell that folder from one another home backs up to, so it also starts this home's first run in a folder that holds another home's backups. It has no time limit of its own: it sends what changed since the last run, which is usually little, and a first run it finishes stops at the tick's end and goes on next tick. A target that isn't there, such as an unplugged drive, fails the tick's backup step every tick until it's back.
- MCP doesn't report backups: they are the owner's, and a client sees only sessions.
- A new backup key (`distill backup new-key`, or Make a new key… on Setup's Backups step) replaces the old one, and the home keeps no copy of it: the owner's copy of the old key is the only way to open what was backed up under it. Every target starts over, sending everything again; what it held stays (no pruning exists yet), so a target holds both copies. Restore and verify take one key, and find only the runs made under it.
- Every file of the backup set but `raw/` and the two logs is stored whole whenever it changes. The read log, the backup log and the manifest are stored as what each run appended, in parts that merge as a binary counter carries: a record lists at most log2(runs) + 1 parts of each, and each appended byte is stored again at most that many times. A log that no longer starts with what was stored is stored again from its start.
- A folder target's first run can't tell an empty folder from a drive's mount point with the drive away (on Linux; on macOS the mount point goes with the drive), so it takes the folder; after its first successful run, a target without its `distill-backup/` folder is refused.
- A target learns how many objects it holds, their sizes and when they arrive (ADR 0009). Nothing on a target is ever deleted, so it only grows.
- A blob lost from this machine's archive before any backup took it can't be sent: the run stores the rest, then fails, counting it as missing.
- `distill restore` brings back only the newest run, from a folder target (`--folder`) or an adapter target (`--kind` with its settings as `--set key=value`), and only into an empty home whose parent folder exists; it never merges into a live one. It brings back the backup set alone: the next tick rebuilds sessions, findings and the index, and makes cards (unless the target carries them) and personal details again at model cost. Harness files DISTILL never captured, and anything after the newest run, are not in a backup. The restored backup log lacks the newest run's own line.
- A restore stops when the target lacks a blob the manifest names, unless `--allow-missing` is given. It takes the backup key from `--key-file` or a pipe, never typed at the terminal, where it would show on screen.

## The window

- Findings are covered with a chip naming their kind rather than blurred (ADR 0007). The list's chips are not clickable; a finding is shown only in an open session. A covered secret copies as its chip, a shown one as its value.
- The session view has no search inside a session and no jump to the passage a search matched; it reads the whole session at once.
- Approvals shows only pending requests; answered, collected and expired ones are in the read log. A request's expiry is recorded when the next call touches requests.
- Setup cannot move the home, and offers `sessions_per_run` as 25, 50, 100 or 200 (another value set by hand is kept until one is picked). It offers the models stored on this machine, or, when cards and detection run at a trusted service (`[steward.generation]`), the models that service lists when checked (plus the one already set). It takes the service's key as a file path, not the key itself.
- A previous build's `recipes/`, `exports/` and `steward/` folders in the home are reported by the exposure check and otherwise ignored, never deleted.
